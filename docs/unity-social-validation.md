## 准备

1. 从项目根目录启动已有后端：
   ```powershell
   dotnet run --project backend/SocialSystem.Api --launch-profile http --no-build
   ```
2. 使用 Swagger 准备 A、B 两个不同账号。登录后可从主页读取各自用户 ID。
3. Unity 打开已有 LoginScene 并 Play，或运行 Build/SocialSystem.Client.exe。可使用 Editor + exe 分别登录两账号，也可逐次退出切换账号。
4. 不需要手工挂脚本。新增页面运行时自动创建；默认 HTTP 地址在 ClientServices 的 ApiClient 中修改。

## 用户主页验收

1. 用 A 登录，看到昵称、账号和用户 ID；密码框应已清空。
2. 点击“退出登录”，返回登录页；用 B 登录，应显示 B 的身份。
3. 输入错误密码应留在登录页，不能进入业务页面。
4. 业务页面令牌到期或请求返回 401 时应回到登录页，重新登录可以继续。

## 好友模块验收

1. A 打开“好友”，检查空列表或已有列表。
2. 输入 B 的用户 ID，点击“发送好友申请”，记录状态区返回的申请 ID。
3. A 再次提交应提示已有待处理申请；A 填入该申请 ID 接受应被拒绝。
4. B 登录后在“收到的申请 ID”中填入该 ID，点击“接受申请”。双方刷新后应出现对方昵称、账号、用户 ID。
5. 点击“删除好友”后需再次“确认删除”才执行；双方刷新后关系消失。后续聊天验收前重新申请并接受。
6. 超过 10 个好友时检查上一页/下一页；首页和末页的对应按钮应禁用。无效 ID 或自己 ID 应给出明确提示。

限制：没有自动申请列表或搜索。接收方的申请 ID 由发送方告知，不等同于用户 ID。

## 聊天模块验收

1. A 在好友列表点击 B 的“聊天”，确认会话标题及用户 ID。
2. A 发送中文、多行内容；B 进入与 A 的会话，点击“查看 / 刷新历史”后回复。
3. 两端刷新应看到相同的双方消息，按时间顺序显示，“我/对方”与当前账号一致。
4. 空白消息不能发送，输入框最多 2000 字符；包含 <b> 等字符的内容应按原文显示。
5. 修改对方 ID 后，需先点击“查看 / 刷新历史”确认会话，避免误发。
6. 删除好友后可按用户 ID 查历史，但发送应提示仅好友可发送，失败输入应保留。

限制：没有自动推送，每次查询返回完整历史；使用滚轮查看长会话。

## 动态模块验收

1. A 打开“动态”，输入多行内容并发布；列表应出现作者、时间和正文。空白不能发布，最多 2000 字符。
2. B 刷新应看到 A 的动态。B 发表评论后评论数增加；评论最多 500 字符。
3. 本次会话最近提交的评论应标明来源；界面不会把它冒充完整历史评论。
4. B 点赞后按钮变为“取消点赞”，数量增加；取消后数量恢复。A 刷新看到数量变化，但自身点赞状态独立。
5. B 不应看到 A 动态的删除按钮；A 删除自己的动态需要再次确认，刷新后消失。
6. 超过 10 条动态时检查分页；测试长正文滚动、中文昵称、切换窗口尺寸时控件能否阅读和点击。

限制：所有登录用户都可见的广场，不是仅好友动态；历史评论查询 API 尚不存在。

## 故障与退出验收

- 停止后端后刷新：显示连接错误，请求结束后按钮恢复；启动后端再次刷新可恢复。
- 写请求超时不自动重试，应先刷新确认是否提交成功。
- 请求进行中禁用业务操作，结束后恢复；重复快速点击不应重复提交。
- 退出 A 再登录 B，好友/消息/动态状态不得残留 A 的数据。
